# ARG, isolated challenges, and physical artifacts

These are authored puzzle briefs, not an authorization to investigate outside systems. Use project-owned static artifacts or isolated local containers with explicit target/rate rules. No third-party systems, live credential use, personal-data harvesting, malware, persistence, or social engineering is part of the fiction.

## Puzzle 1 — The missing line

Objective: explain the witness seam and introduce evidence ordering. Ship three accessible SVG/static image artifacts with six indexed fragments each. The intended solution orders fragments by the printed calibration index, reads the deliberately missing positions, and decodes their supplied hexadecimal byte pairs to an authored short phrase. The answer is a story key, not a credential.

Hint ladder at release, +24h, and +48h: “The order is already visible”; show where calibration indices live; demonstrate one byte conversion. Provide a screen-reader transcript with the same information, not a solution hidden exclusively in color or image metadata. Accept a short explanation of method, not only a copyable final string. Publish the worked solution after the event.

Validation: bounded form input, keyed server-side answer normalization, atomic submission idempotency, 5 attempts/minute/session, review copied explanations without collecting device fingerprints. Rate limits reduce spam, not proof sharing. Reward a reviewed allowlist application or archive credit according to published availability; never promise a valuable asset to every solve.

## Puzzle 2 — Contradictory permission logs

Objective: reveal the administrator's voluntary revocation. Ship a sandboxed fictional event viewer, synthetic logs, and an explicit local scope file. An intentionally inconsistent event order is resolved by comparing supplied monotonic sequence numbers and a published SHA-256 checksum manifest. No exploitation of a real service is required.

For an optional CTF variant, run a deliberately vulnerable toy authorization service in an isolated container with two provided fake accounts and synthetic documents. The educational objective is to explain why checking a UI role is not object authorization. Restrict egress, reset containers between players, publish exact authorized endpoints, cap requests, and prohibit scanning outside the lab. Do not include real cloud keys or production service credentials.

Hint ladder: inspect the two provided account views; compare the documented object IDs; explain the missing object-owner check. Offer the same story completion via a nontechnical log-analysis route. Publish a safe local reproduction and the corrected handler after the event.

For holders, early chapter eligibility is issued as a token-bound scoped attestation. Solving does not authorize a wallet transaction automatically; the owner still selects the state action. At the fixed fallback date every holder can advance without puzzle service availability.

## Authoring and safety gates

Each event needs a named puzzle author, independent solver, intended path, source artifacts and hashes, accessible equivalent, hint schedule, bounds, scoring rubric, reward inventory, expiry, abuse report channel, and public writeup. Keep unreleased answers in private authoring storage, not a public frontend bundle. Source-code puzzle clues must be intentional and contain no unrelated configuration.

Every security-themed live lab must first have populated `scope.yaml`, `authorization_ack: true`, owned accounts, program notes/rules, rate/concurrency/timeout/request caps, a timestamped evidence path, and `KILL-CONDITIONS.md`. This design release does not create authorization on behalf of a future platform or third party.

## Physical ROOT card

Produce a small optional prototype run only after budget, manufacturing tolerances, materials, and fulfillment are reviewed. Card serial maps to a public artifact page. A passive NFC tag opens the same page as the printed URL; because it can be copied, it proves neither genuine hardware nor token ownership. Never embed recovery phrases, private keys, admin access, or executable downloads.

Optional wallet linking is a scoped signed session with nonce/expiry and an unlink action. Ownership is checked on-chain; a physical scan alone never advances state or transfers an NFT. A future secure-element card would need challenge-response design, lost-card recovery, clone testing, and an independent review before any authentication claim.
